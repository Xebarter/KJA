================================================================================
KJA DESKTOP ↔ WEB DASHBOARD PARITY GUIDE For agents building / editing
Flutter Desktop App office & teacher pages. STRICT. Do not invent a
parallel design system. Match the web app.
================================================================================

PURPOSE

Every Desktop App dashboard page must look and behave like the
corresponding web office page — same layout hierarchy, copy, icons,
tones, filters, empty states, and interaction patterns. The Desktop App
is a Windows port of the web desks, not a redesign.

If you cannot match a control pixel-for-pixel, match structure +
tokens + copy first, then refine. Never ship a generic Material “table +
AppBar” stand-in when the web page has a hero, KPIs, panels, tabs, or
boards.

================================================================================
0. HARD RULES (NON-NEGOTIABLE)
================================================================================

1.  SOURCE OF TRUTH = WEB

    -   Open the live web route (or its React/CSS source) BEFORE writing
        Flutter UI.
    -   Copy titles, kickers, ledes, button labels, empty-state text,
        column headers, and status labels from the web — do not
        paraphrase.

2.  NO PARALLEL AESTHETIC

    -   Do not introduce new brand colours, fonts, card radii, or button
        styles.
    -   Do not use default Flutter purple, Material 3 tonal surfaces, or
        Segoe-only UI.
    -   Do not replace Font Awesome icons with Material Icons when the
        web uses FA.

3.  REUSE DESKTOP PRIMITIVES Prefer existing helpers over one-off
    decoration:

    -   Desktop App/lib/theme/desk_theme.dart → DeskColors, DeskFonts
    -   Desktop App/lib/widgets/office_chrome.dart → DeskHero,
        DeskOfficeScaffold, OovStatCard, OovCard, OfficeTone,
        DeskReveal, SexMixBar, …
    -   Desktop App/lib/widgets/desk_page.dart → DeskPageScaffold,
        DeskCard, DeskDataTable (simple pages only)
    -   Desktop App/lib/widgets/fa_icon.dart → FaIcon(‘fa-…’)
    -   Desktop App/lib/access/nav_config.dart → routes, labels, icons

4.  EXTEND FA MAP WHEN NEEDED If the web uses an FA icon not in
    fa_icon.dart, ADD the mapping — do not substitute a different icon
    “close enough”.

5.  DATA + ACTIONS MUST MATCH WEB Same filters, same columns, same
    primary actions, same status transitions. Offline/outbox is
    Desktop-only chrome; it must not replace web UI.

6.  FINISH THE CHECKLIST A page is not done until every item in §9
    PERFECTCTION CHECKLIST is checked.

================================================================================
13. INSTANT NAVIGATION, WARM PAGES & PERCEIVED PERFORMANCE
(NON-NEGOTIABLE)
================================================================================

GOAL

Every page must feel immediate when clicked, while preserving the web
dashboard’s appearance, content, behaviour, permissions, and data
semantics. “Instant” means the page shell and meaningful UI appear
immediately, and previously loaded data is shown immediately when safe.
It does NOT mean hiding errors, showing fabricated data, or pretending a
server mutation succeeded.

13.1 PERFORMANCE ACCEPTANCE TARGETS

Use these as engineering targets, not excuses to fake readiness: -
Navigation feedback: immediate in the same interaction/frame where
practical. - First meaningful page frame: target <= 100 ms on a normal
desktop after a page has been visited or its route has been warmed. -
Cached page content: show synchronously from memory/local cache where
valid. - Freshness refresh: run in the background without blocking the
page shell. - Typical route change: no full-window spinner, blank
screen, or unnecessary rebuild of the whole application. - Large tables:
render the visible rows first; paginate/virtualize the rest. - Measure
cold start, first visit, repeat visit, and slow/offline operation
separately. Never claim instant performance without measuring it.

13.2 REQUIRED NAVIGATION ARCHITECTURE

Before implementing a page, inspect the existing app’s router, shell,
state management, repository, cache, and sync architecture. Extend the
architecture already used by the project; do not introduce a second
competing pattern.

-   Keep DeskShell / the persistent application chrome mounted across
    route changes. Do not recreate the sidebar, top bar, session state,
    or global providers for each page.
-   Use GoRouter route definitions and stable page identities. Avoid
    rebuilding the entire app for a child-route change.
-   Use a shared page host/scaffold so page transitions, content
    constraints, scroll behaviour, and loading states are consistent.
-   Keep route construction cheap and synchronous. Do not perform
    network calls, expensive parsing, large sorting operations, or file
    I/O inside build().
-   Do not put async work in a widget constructor or trigger duplicate
    requests from build(). Start it in a provider/repository lifecycle
    or an explicit refresh action.
-   Use const widgets where possible and stable keys where identity
    matters.
-   Keep page-local state local; keep cross-page/session state in the
    existing shared state solution. Avoid a global rebuild when only one
    page changes.
-   Do not create and dispose the same expensive controller/provider on
    every navigation unless that lifecycle is necessary.
-   Use a lightweight transition consistent with the product; never use
    a long transition to conceal loading.

13.3 PRELOAD / WARM ROUTES INTELLIGENTLY

Warm only routes that the signed-in user is permitted to access.

-   On app startup, load the session, grants, navigation configuration,
    and essential shell data once. Do not block the shell on every
    dashboard’s data.
-   After the shell is ready, pre-initialize cheap page providers and
    metadata for likely next destinations, especially pages directly
    visible in the sidebar.
-   When idle, prefetch small, safe read-only datasets for
    high-probability routes. Prioritize likely destinations and stop
    speculative work when the app is busy, offline, or under memory
    pressure.
-   Do not prefetch every route or every large table. Use a bounded
    cache with expiry and memory limits.
-   Do not prefetch sensitive data before authorization is confirmed.
-   Avoid duplicate prefetch + page-load requests.
    Providers/repositories must deduplicate in-flight requests by query
    key.
-   Do not warm routes by secretly triggering mutations or actions.
-   If the app has many routes, warm the current route and its most
    likely adjacent destinations first; expand only after measuring
    benefits.

13.4 SHOW THE PAGE IMMEDIATELY; LOAD DATA PROGRESSIVELY

Separate the page frame from its data state.

1.  Build the header, correct panels, toolbars, filters, tabs, and
    content layout immediately using the exact web copy and dimensions.
2.  If valid cached data exists, render it immediately and mark it stale
    internally if a refresh is required.
3.  Refresh data asynchronously in the background.
4.  Update only the affected widgets when the response arrives.
5.  If no cache exists, use the web-equivalent skeleton/loading
    treatment inside the correct layout rather than a blank page or
    full-window spinner.
6.  If refresh fails but valid cached data exists, retain it and show a
    restrained, accurate stale/offline notice. If no data exists, show
    the proper error state and retry action.
7.  Never replace real data with demo rows, hardcoded counts, fabricated
    chart values, or fake success messages.

Use stale-while-revalidate only where the data’s security and business
meaning allow it. Do not show stale data as current when that could
cause a harmful decision. For financial balances, permissions,
attendance, marks, admissions decisions, and other sensitive/high-impact
state, clearly communicate freshness and revalidate before consequential
actions.

13.5 CACHING CONTRACT

Create or reuse a repository/cache layer instead of caching ad hoc
inside widgets.

Every cache entry should be keyed by all inputs that affect the result,
including where applicable: - signed-in user / tenant / school /
dashboard access scope; - route or resource type; - filters, search
query, sort order, page/cursor, and selected academic period; - relevant
record IDs and query parameters.

Requirements: - Never reuse one user’s or school’s cache for another
user’s session. - Clear or invalidate sensitive caches on logout,
account switch, permission changes, school/tenant switch, and relevant
mutations. - Use a documented TTL/freshness policy appropriate to each
resource. - Invalidate or update affected cache entries after
create/update/delete/status changes. Update visible UI only when the
backend confirms success, or clearly label a supported optimistic update
and roll it back on failure. - Keep cached data modelled and
versionable; handle schema changes safely. - If offline mode and an
outbox exist, distinguish queued, syncing, synced, failed, and conflict
states. Never label a queued write as completed on the server. - Do not
persist highly sensitive data to disk unless the existing security
design explicitly permits it and storage is protected appropriately. -
Test cache invalidation, logout, switching accounts, permission
revocation, and stale data behaviour.

13.6 SEARCH, FILTERS, TABLES AND LARGE DATASETS

-   Debounce free-text search using the web app’s semantics. Cancel or
    disregard obsolete responses so an older query cannot overwrite
    newer results.
-   Keep search text, filters, sort, selection, and pagination stable
    when returning to a page if the web app preserves them.
-   Avoid fetching the whole dataset when the web uses server-side
    filtering or pagination.
-   Use server-side pagination/filtering for large datasets where
    supported.
-   Use Flutter’s appropriate lazy/virtualized list/table strategy for
    large row counts. Do not build thousands of rows eagerly.
-   Preserve the web’s exact visible columns, order, formatting, empty
    states, row actions, and selection rules.
-   Cache only the pages/query combinations that are useful; avoid
    unbounded caches for every search string.
-   Keep scrolling smooth; do not perform sorting, filtering, or
    expensive formatting synchronously on the UI thread for large
    collections.
-   Keep keyboard navigation, focus order, selection, and mouse
    interactions natural for Windows desktop.

13.7 ASYNC REQUEST AND ERROR DISCIPLINE

-   Deduplicate simultaneous requests for the same resource/query.
-   Cancel requests where the networking stack supports cancellation;
    otherwise use request IDs/query keys to ignore stale responses.
-   Add explicit loading, success, empty, stale, error, and unauthorized
    states.
-   Avoid retry loops. Retry transient failures with bounded backoff and
    expose a manual retry action where appropriate.
-   Distinguish no records from failed-to-load records.
-   Do not swallow exceptions or leave a permanent spinner after
    failure.
-   Do not let a slow secondary panel block the whole page if other
    sections can render independently.
-   Use request timeouts and clear feedback for a disconnected service.
-   Keep network and data transformation work out of the Flutter UI
    isolate when measurements show it blocks frames; use isolates for
    genuinely expensive CPU work, not as a default for every operation.

13.8 DATA LAYER AND WEB CONTRACT PARITY

-   Reuse the same backend tables, RPCs, business rules, validation, and
    access controls as the web application wherever possible.
-   Share typed domain models and validation rules when the codebase
    supports it. Do not copy business logic into multiple places if it
    can be safely shared.
-   Keep presentation widgets separate from repositories, providers, and
    data models.
-   Treat UI hiding as presentation only; backend authorization remains
    mandatory.
-   Match the web’s sorting, filtering, pagination, status transitions,
    and mutation semantics, including edge cases and permission checks.
-   Do not invent a new endpoint, database field, status, or fallback
    business rule without inspecting the web implementation and backend
    contract.
-   Before changing a mutation, identify its authoritative source of
    truth and success/failure response. Ensure the desktop UI cannot
    silently diverge.

13.9 PERF INSTRUMENTATION AND PROFILING

For each page, measure: - click-to-route activation; - route activation
to first meaningful frame; - cache hit/miss and cache age; - request
duration and response size; - time until primary content is usable; -
unnecessary widget rebuilds; - frame jank while scrolling and
filtering; - cold-start versus repeat-navigation timings.

Use Flutter DevTools Performance, CPU Profiler, Memory tools, and
rebuild profiling as appropriate. Test both debug and profile/release
modes; debug timings are not representative of production performance.

Fix measured bottlenecks in this order: 1. Remove blocking work from
build() and route activation. 2. Keep the shell and shared state alive.
3. Render the page frame and cached data first. 4. Deduplicate and
parallelize independent read requests. 5. Reduce over-fetching and
payload size. 6. Virtualize large tables/lists. 7. Reduce unnecessary
rebuilds and expensive layout/paint work. 8. Add bounded prefetching
only where measurements justify it.

Do not add complex caching, state-management packages, or
route-preloading systems without checking what the project already uses.
Prefer a small, consistent design.

13.10 PERFORMANCE TEST MATRIX

Every important page must be checked under these conditions: [ ] First
visit after app launch, cache empty. [ ] Second visit with warm cache. [
] Repeatedly switch between two or more pages. [ ] Slow network /
high-latency response. [ ] Offline start and offline navigation where
supported. [ ] Expired cache with background refresh. [ ] Large
realistic dataset. [ ] Search rapidly while previous requests are still
running. [ ] Mutation followed by navigation away and back. [ ]
Logout/login as another user or school. [ ] Permission removed while app
is open. [ ] Failed request followed by retry.

Acceptance: - Navigation always gives immediate visual feedback. - The
shell does not flash, reset, or reload unnecessarily. - No page displays
fabricated or cross-user data. - No old response overwrites the newest
search/filter result. - No unbounded cache growth or duplicate request
storm. - Errors and offline states are truthful and recoverable.

14. VISUAL FIDELITY ENGINEERING: EXACT WEB-TO-DESKTOP RECONSTRUCTION
================================================================================

The goal is not “inspired by the web page.” The goal is a faithful
reconstruction of the same product surface in Flutter, at the same
desktop viewport and with the same data state.

14.1 INSPECT BEFORE CODING

For every prompt, the agent MUST: 1. Identify the exact web route and
the user’s intended state (default, filtered, selected tab, modal open,
empty state, etc.). 2. Open the running web page at a desktop viewport
and inspect it visually. 3. Read its page.tsx/tsx/jsx source, CSS,
shared components, theme tokens, icon names, fonts, and relevant data
loader/actions. 4. Inspect the current Flutter counterpart, shell,
reusable widgets, route config, theme, models, repository, and tests. 5.
Record an implementation map before coding: web source files, Flutter
files, components to reuse, data contracts, exact interactions, and
known differences. 6. If the web route/source is unavailable, state that
limitation and inspect the closest authoritative source. Do not pretend
an uninspected page is exact.

14.2 USE SCREENSHOTS AS A TESTABLE SPECIFICATION

Capture the web and desktop at the same window dimensions, display
scale, and equivalent data/state. Compare: - overall page and shell
geometry; - content width and horizontal alignment; - header position,
height, wrapping, and action placement; - card and panel bounds, gaps,
padding, borders, radii, and shadows; - text content, font family, size,
weight, line height, and wrapping; - icon family, glyph, size, baseline,
and colour; - table row height, column width, alignment, status chips,
and separators; - scroll positions, sticky elements, and overflow; -
hover, focus, pressed, selected, disabled, loading, empty, and error
states.

Use image overlays or pixel-difference tooling when available. A
screenshot is a verification aid, not permission to ignore behaviour or
source code. Correct the largest visible differences first, then repeat
the comparison.

14.3 TOKEN AND ASSET PARITY

-   Use the existing DeskColors, DeskFonts, OfficeTone, shared widgets,
    and FA map described in this guide. Inspect actual source tokens
    when values conflict with this guide; the current web source is
    authoritative.
-   Reuse the exact logo, SVG/image assets, icon package and icon names
    where possible.
-   Ensure Roboto and Yantramanav font files are actually bundled/loaded
    in the desktop app; merely naming a missing font does not guarantee
    parity.
-   Do not substitute a similar icon or use emoji for branded UI icons.
-   Do not introduce gradients, new brand colours, extra decorative
    elements, or a new design language unless the web page itself uses
    them.
-   Account for platform rendering differences, but do not use them as
    an excuse for avoidable differences in font, sizing, spacing, or
    component structure.

14.4 MATCH INTERACTION, NOT JUST THE SCREENSHOT

For every visible control, document and implement: - its default
state; - hover, focus, pressed, selected, and disabled states as
applicable; - keyboard/mouse behaviour; - validation and confirmation; -
loading and failure behaviour; - data/backend effect; - destination or
state after activation.

A button that looks correct but does nothing is not parity. A filter
that changes its label but not the results is not parity. A table action
that bypasses the web’s validation or permission checks is not parity.

14.5 SHARED COMPONENT STRATEGY

-   Prefer existing shared Flutter primitives and improve them centrally
    when the same parity issue affects several pages.
-   Extract a new reusable component only when there is a real repeated
    pattern.
-   Keep page-specific composition close to the page implementation.
-   Do not build a universal abstraction that makes simple pages hard to
    implement.
-   Do not duplicate the sidebar, header shell, theme tokens, icon map,
    or backend logic inside individual page files.
-   Avoid changing shared primitives in ways that break already-matched
    pages. Run regression screenshots/tests for representative pages
    after shared changes.

================================================================================
15. AGENT EXECUTION PROTOCOL FOR EACH USER PROMPT
================================================================================

When the user asks to build, rebuild, or modify a particular desktop
page:

PHASE 1 — IDENTIFY [ ] Resolve the exact desktop route and corresponding
web route. [ ] Confirm which dashboard, role, access grants, and target
viewport apply. [ ] Determine the expected default state and any
explicitly requested state. [ ] Read the authoritative web source and
current Flutter implementation.

PHASE 2 — SPECIFY [ ] Write a concise parity map: structure, tokens,
assets, copy, controls, data source, permissions, and navigation
outcomes. [ ] List page states: loading, cached/stale, success, empty,
error, offline, unauthorized, and mutation-in-progress where relevant. [
] Identify what can be reused, what must be created, and what must not
change. [ ] Identify performance risks and choose the simplest solution
that meets targets.

PHASE 3 — IMPLEMENT [ ] Implement the page frame so it appears without
waiting for network requests. [ ] Use the shared shell and established
theme/components. [ ] Match web content order, exact copy, icon names,
tokens, and geometry. [ ] Connect real repositories/providers and the
same backend contracts. [ ] Keep expensive work out of build() and
deduplicate async reads. [ ] Add bounded caching/prefetch only where
useful and secure. [ ] Preserve existing routes, grants, keyboard/mouse
behaviour, and neighbouring pages. Do not replace real functionality
with placeholders.

PHASE 4 — VERIFY [ ] Run flutter analyze. [ ] Run relevant
unit/widget/integration tests. [ ] Launch the Windows desktop app and
the matching web route side-by-side. [ ] Compare screenshots at
equivalent viewport, scale, data, and UI state. [ ] Test every visible
interaction and relevant loading/error/access state. [ ] Test cold and
warm navigation and profile the page if it feels slow. [ ] Fix
regressions in shared shell, navigation, theme, and other pages.

PHASE 5 — REPORT Before declaring completion, report: - exact web route
and source files inspected; - Flutter files created/modified; -
components and backend contracts reused; - visual differences that
remain and why; - performance checks performed and measured results; -
tests/analyze results; - any unresolved issue, clearly labelled.

Do not claim a screenshot comparison, test, or performance measurement
was done if it was not actually performed. Do not report “done” while
required checks remain.

================================================================================
16. FINAL PAGE ACCEPTANCE GATE
================================================================================

A page may be marked COMPLETE only if all applicable conditions pass:

VISUAL [ ] Correct web route/source inspected. [ ] Same hierarchy, copy,
icons, assets, typography, colours, spacing, and controls. [ ]
Side-by-side screenshot comparison completed at equivalent desktop
dimensions. [ ] All important visual differences corrected or explicitly
documented.

FUNCTIONAL [ ] Every visible control works and matches web semantics. [
] Real data, validation, authorization, and mutations use correct
contracts. [ ] Loading, empty, error, offline, stale, and no-access
states are honest and clear. [ ] Mouse, keyboard, focus, scrolling, and
selection behaviour are usable.

PERFORMANCE [ ] Page frame appears without waiting for network data. [ ]
Repeat navigation uses valid cache where appropriate. [ ] Background
refresh does not blank or unnecessarily rebuild the page. [ ] Requests
are deduplicated; stale responses cannot overwrite current state. [ ]
Large collections do not render all rows eagerly. [ ] Cold/warm
navigation and realistic data have been tested. [ ] No unbounded cache,
unsafe cross-user data reuse, or fake instant loading.

ENGINEERING [ ] flutter analyze clean on touched files. [ ] Relevant
tests pass, or failures are reported accurately. [ ] No unrelated page,
shell, route, permission, or design regression. [ ] Completion report
states what was actually verified.

If any important criterion fails, the page is NOT COMPLETE. Match the
web app; make navigation feel instant through architecture and
progressive rendering, not by removing content, faking data, or
weakening correctness.
